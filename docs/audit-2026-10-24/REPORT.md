## 1. 结论

项目已具备独立聊天前端的主要能力：角色与聊天管理、OpenAI 兼容连接、预设与世界书、正则、数据库填表、虚拟列表、手动更新。模块化方向合理，数据保留、兼容性校验与部分失败恢复已有明确设计。

当前主要短板是 **main.js 中跨模块状态的异常恢复，以及自动填表调度缺少端到端回归覆盖**。发现并隔离复现 5 个问题，其中 2 个 P1、3 个 P2。现有测试通过不能替代这些场景的验证。建议先修复 P1，再补齐自动填表与错误恢复测试，之后开展实机和真实后端验收。

优先级定义：P1 为可能导致数据归属错误或越过权限边界、应优先修复的问题；P2 为确定的功能错误，安排近期修复。未发现并确认 P0 问题，但此次审查不构成全面安全认证。

## 2. 项目定位与代码结构

这不是完整 SillyTavern，也不是原生扩展：静态前端挂载于宿主 `/app/`，通过宿主会话与 CSRF 调用原生 API。仓库另含一个 Node.js 服务端插件和安装/发布脚本。根 README 中“只包含前端源码”的说法已不完全准确。

基线有 64 个 Git 跟踪文件；主要应用 JS 共 27 个（不含 vendor 与测试）。无 package.json、前端构建链或仓库内 CI 配置。应用直接使用浏览器 ES Modules，测试使用 Node 内置测试运行器。本次运行环境为 Windows PowerShell、Node v24.21.0。

### 数据存储与边界

- 聊天通过 `/api/chats/save` 写入宿主 JSONL，包含元数据、完整消息、分支与数据库快照。
- 设置主要写入 `settings.json` 的 `independent_frontend`；全局正则、世界书、persona 还会使用原生字段。
- 连接列表与当前连接保存在用户文件 `independent-frontend-connections.json`，包含明文 `proxyPassword`；同时使用宿主 secrets 接口注册请求用的 secret ID。
- 当前预设名称独立保存在 `independent-frontend-preset.json`，预设正文仍在宿主预设目录。
- 数据库附着于 AI 消息的 `TavernDB_ACU_Data`，部分元数据与历史快照保存在聊天头；不是单独数据库服务。
- 更新插件替换宿主共享 `public/app`；`/recent`、`/bootstrap` 则读取当前用户目录。共享代码与用户数据是两种不同权限范围。

## 3. 关键流程

### 启动和聊天

连接宿主并获取 CSRF → 读取启动设置与预设 → 初始化连接/首页 → 读取角色和聊天 → 建立内存状态 → 虚拟列表渲染。连接失败已有单独状态，预设缺失也不会静默切到第一份。

### 生成和保存

校验 busy/dirty/连接/预设 → 输入正则 → 世界书、宏、数据库与历史组装 → 后端 tokenizer 精确计数并按需裁剪 → 保存用户消息 → 请求模型 → SSE 或普通 JSON 解析 → 输出正则 → 保存完整聊天 → 可选自动填表。

优点：上下文裁剪不直接改写磁盘历史；未保存状态会阻止部分后续操作；流式中断保留已收到文本；设置写入前读取最新快照，减少同页面覆盖冲突。

### 更新

用户手动检查 → 对比 revision → 用户确认 → 插件获取远端清单 → 路径/数量/大小/SHA-256 校验 → 暂存目录 → 旧目录备份与目录切换 → 清理。固定来源与校验能防止误路径和损坏文件，但清单与内容同源，不能抵御发布仓库本身被控制。更新文件来自可变 main 分支，发布期间发生变化会校验失败并要求重试。

## 4. 已确认问题

### F1 · P1：角色切换失败后，新角色与旧聊天状态混用

位置：[`main.js:379`](../../public/app/main.js#L379)，相关保存入口 `main.js:415–423`。

`openCharacter()` 在 `loadChat()` 成功之前就将 `state.character` 换成新角色。若聊天读取失败，finally 仅解除 loading，没有恢复旧角色；旧 `file/header/chat` 仍保留。随后保存会组合成新角色头像、旧聊天文件名和旧聊天正文。

复现：打开 A 的聊天，切到 B，模拟 B 的聊天读取失败，再调用保存。隔离探针捕获到保存参数为 **B.png / A-chat / A 的正文**。

影响：后续编辑或发送可能把 A 的内容提交到 B 的聊天目录；是否落盘取决于宿主文件是否存在及完整性校验。即使宿主拒绝，也已经出现角色与历史混用，可能使发给模型的角色上下文错误。本次未向真实用户目录写入。

建议：将角色、文件名、聊天头和正文作为一个切换事务；先加载到局部变量，全部成功后一次性提交。失败时保持旧状态。回归测试应同时断言渲染、下一次保存和生成的目标身份。

### F2 · P2：默认自动填表范围无法前进

位置：[`main.js:1517`](../../public/app/main.js#L1517)，关联 `main.js:1464–1465`、`database-defaults.js:14–15`。

默认 `updateBatchSize=1`。对于“AI 开场白(0)、用户(1)、AI 回复(2)”的常见聊天，自动逻辑生成范围 `[0,1]`，实际更新只处理范围内的 AI 开场白。快照写在 0 楼，但下一轮查找进度的循环排除了 0 楼，并仍用 0 表示未处理；后续继续选择 `[0,1]`。

即使快照位于非零 AI 楼，下一批只包含紧接着的用户楼时，`updateDatabase()` 也会因没有 AI 楼直接返回，进度不再前进。

复现输出：两次新回复后的调用范围均为 `[[0,1],[0,1]]`。探针对自动调度执行原函数，并模拟第一次快照附着在 0 楼。

影响：自动填表可能重复消耗模型调用处理开场白，或长期提示无消息可更新，无法覆盖新回复。

建议：分别表示“未处理”和“已处理到 0 楼”；明确批量单位是消息楼还是 AI 轮次，计算范围时保证包含下一个待处理 AI 楼。补充有/无开场白、batch=1/2、多轮对话、skip>0 测试。`autoStart` 目前写入但未被调度读取，也应明确是否保留此语义。

### F3 · P1：普通登录用户可调用共享前端更新接口

位置：[`server/st-new-updater/index.mjs:56`](../../server/st-new-updater/index.mjs#L56)。

`/install` 未检查管理员身份，而它会替换所有用户共享的 `public/app`。邻接宿主源码中，`server-main.js:248` 提供登录保护，`plugin-loader.js:213–222` 直接挂载插件路由，未附加管理员保护；宿主已有 `requireAdminMiddleware` 可作为实现参照。

复现：向原路由处理器传入 `user.profile.admin=false`，请求仍进入下载阶段，没有返回 403。探针在 fetch 处主动终止，没有网络访问和目录替换。

影响条件：启用服务端插件且宿主存在非管理员用户。普通用户可触发全站前端版本切换或占用更新流程。**不是匿名任意文件写入**：宿主仍有登录/CSRF，下载来源与路径受限。

建议：服务端在下载前校验管理员权限；前端隐藏无权限入口只能作为体验补充。添加管理员、普通用户、缺失用户三类授权测试。宿主判断依据来自本地 SillyTavern 副本，其他部署版本仍需核对。

### F4 · P2：正则不存在的捕获组会替换成偏移量或整段原文

位置：[`regex.js:45`](../../public/app/regex.js#L45)。

String.replace 回调参数在捕获组之后还有 offset、原文及可选 named groups。当前直接读取 `args[Number(number)]`，没有约束捕获组范围。

复现：`findRegex='/secret/g'`（无捕获组），`replaceString='$1'`，输入 `secret`，输出为字符串 `"0"`。类似越界索引还可能读取整段原文。

影响：导入规则或用户误配时，消息/提示词被意外插入偏移量或重复全文；raw 阶段处理结果还可能保存到聊天。

建议：分离尾部元参数并只读取合法捕获组；明确不存在捕获组的兼容行为。覆盖无捕获组、可选组、命名组、多位索引与多个匹配位置。

### F5 · P2：默认填表提示要求的“无变化”被解析器当成错误

位置：[`database.js:4`](../../public/app/database.js#L4)、[`database.js:101`](../../public/app/database.js#L101)。

默认提示明确允许“没有变化时输出空 operations”，但 `parseUpdate()` 对 `!result.changed` 一律抛错。

复现：输入合法 `<dataUpdate>{"operations":[]}</dataUpdate>` 被拒绝。

影响：AI 正确遵循提示返回无变化时，界面报告失败，处理进度也无法正常提交，下次可能反复处理相同对话。此问题适用于使用该默认/回退提示的配置，不代表所有参考预设都会输出这个格式。

建议：区分合法无变化、解析失败、操作失败。无变化也应有成功完成及进度推进语义，数据可保持不变。现有测试中存在空 operations 抛错断言，需要同步修订合同与测试。

## 5. 设计风险与维护建议（不计入上述已确认缺陷）

1. **业务编排集中。** main.js 同时持有 UI、持久化、生成和数据库流程，关键异常路径难以独立测试。优先拆出聊天会话事务、生成服务和自动填表调度，避免先做大规模目录重构。
2. **并发保存和跨标签页一致性。** 设置写队列只覆盖单个 TavernAPI 实例；跨页面仍是整文件读改写。聊天 dirty 是布尔值，任一排队保存成功即可清除，宜引入修改版本/保存版本并补充交错测试。此项未独立证明实际 UI 可触发，作为待验证风险。
3. **密钥存储需要准确描述。** 连接文件明文保存密码是已实现的产品选择，不能描述为“仅存在 secret 库”。同用户文件读取者可获取这些密码；备份和导出应按敏感文件处理。未读取任何真实用户连接文件。
4. **HTML 脚本执行边界。** iframe 使用 `allow-scripts` 且没有 `allow-same-origin`，普通 Markdown 使用 DOMPurify；桥接发送前有用户确认。仍允许不受信任脚本运行，存在资源消耗/频繁消息风险；CSP 还允许 Google 字体域名，文档中的“禁止网络”表述过于绝对。现有测试主要检查生成字符串，尚未验证真实浏览器行为。
5. **同步正则和大数据开销。** 导入正则在主线程执行；虚拟列表仅限制 DOM 节点，完整聊天、快照、提示词构建和整段保存仍随历史长度增长。先测点击到请求发出、首字、结束落盘和长消息重绘，再制定优化方案。
6. **发布和安装可恢复性。** 在线更新有暂存/校验，但两次 rename 之间有短暂空窗，进程中断后的自动恢复未实现；Termux 脚本直接覆盖文件且会启用宿主服务端插件开关，缺少前置校验与统一回滚。建议在副本测试中注入失败，记录备份与恢复入口。
7. **文档需收敛。** public/app/README.md 累积多个阶段的说明，包含 HTML 是否运行 JS、密码是否刷新可读、45/79 等历史测试数量的相互冲突描述；DATABASE-PARITY.md 同样是历史验证结果。应保留一份现状说明，将过程记录移到 changelog，明确浏览器/Node/宿主支持版本。
