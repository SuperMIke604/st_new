# 发送与重新生成流程梳理

本文记录发送与重新生成流程。2026-10-24 增加回复完成后的后台资料预加载。

回复保存、自动填表完成后，延迟 150ms 在后台读取关联世界书，并分批准备完整历史（下次发送）和去除末条回复的历史（重新生成）所需的数据库文本与表格宏。世界书沿用 API 的 60 秒读取缓存，缓存失效后正常重新读取；同一路径的进行中读取可复用。资料预加载不会调用模型生成接口，也不会提前抽取世界书概率、展开动态宏或进行最终上下文裁剪与计数。

数据库缓存仅保留两份内存结果；保存聊天时清空，聊天、消息正文、快照、数据库配置或种子改变后重新准备。用户新输入仍完整参与正式请求。加载日志增加“预加载下次生成资料”；预加载失败不会阻止下次发送，下次会正常重试准备。

## 新消息

1. 检查是否正在切换、生成，若有未保存聊天先等待保存。
2. 校验连接和预设，对输入运行输入正则。
3. 组装请求历史并设置 busy，展示“准备上下文”。
4. preparePrompt：读取关联世界书列表和内容，读取当前数据库，展开数据库宏，进入 fitPrompt。
5. fitPrompt：激活世界书、处理提示词正则与宏、组装完整历史；按世界书预算和上下文上限调用后端 tokenizer。需要裁剪时二分搜索历史起点，每个候选都可能重新构建并计数。
6. generationBody 复制最终请求消息。
7. 添加用户楼层、清空输入框，等待 saveChat 完整复制和保存整段聊天。
8. 添加空 AI 楼层，刷新可见消息窗口。
9. 才发出模型 generate 请求。
10. 流式回复每 90ms 最多刷新一次当前消息，重建 Markdown/HTML 显示。
11. 完成后运行输出正则，保存整段聊天、记住聊天入口，解除 busy，按设置检查数据库自动更新。

## 重新生成

共同经过校验、世界书、正则宏、精确计数、上下文裁剪。

区别是去掉末条 AI 回复构建请求；前置复制末条回复用于失败恢复；计数完成后复制末条回复为新候选、保留 swipes/swipe_info，刷新列表后发请求。没有新增用户楼层的前置 saveChat，但已有未保存数据时仍会等待保存。完成后同样整段保存并解除 busy。

## 已确认的潜在开销

| 阶段 | 开销 | 后续应测量 |
|---|---|---|
| 世界书读取 | 列表与正文请求，缓存可能被其他操作清除 | 请求次数、等待时间、缓存命中 |
| 上下文准备 | 对历史运行正则/宏并建立新消息数组 | 构建耗时、历史长度、正文大小 |
| 精确计数 | 多个串行 HTTP tokenizer 请求；不同消息通常不能命中精确缓存 | 调用次数、每次耗时、裁剪迭代数 |
| 新消息前置保存 | 整段结构复制、JSON 序列化、传输和后端落盘 | 保存 payload 大小、前端复制时间、后端响应时间 |
| 重新生成复制 | 末条回复可能附带大量候选与数据库快照 | 复制大小和耗时 |
| 可见区刷新 | 新增楼层改变消息深度，可能使保留窗口内消息重新渲染 | 重绘次数、HTML iframe 重建次数 |
| 流式刷新 | Markdown 转换、清理及 iframe 创建在主线程执行 | 每次刷新耗时、脚本是否重复启动 |
| 结束保存 | 保存完成前 busy 不解除，看起来仍不能继续操作 | 流结束至解除 busy 的时间 |

## 下一步建议

先采集上述各阶段耗时，把“点击至模型请求发出”和“模型请求至首字”分开统计。优先处理确定重复的构建、计数和重绘，再评估保存策略。未经恢复测试，不将必要的保存直接移至后台，也不使用粗略 Token 估算替代精确预算。
