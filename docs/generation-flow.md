# 发送与重新生成流程梳理

本文记录发送与重新生成流程。2026-10-26 对照当前工作区补齐助手事件节点；生成编排、事件顺序或保存边界改变时更新。入口为 `public/app/main.js` 的 `generate/preparePrompt/prepareRoleMvu`、`engine.js` 与脚本运行时。下述旧耗时是历史对照，本次未复测；缓存所有权见 [性能约束](domains/performance.md)。

聊天输入框提交后立即清空，并在末尾显示用户消息卡片。「阅读设置 → 发送延迟（秒）」默认 5 秒，设为 0 即开始准备上下文、派发本轮生成事件并请求模型。等待时点击原位置的停止按钮会取消本轮生成，并保存已显示的用户消息。保存后可直接编辑卡片，留空输入框再次发送可请求这条消息的回复。页面离开时取消待发送操作。重新生成和 APK 已发出请求的恢复沿用原来的入口。

「阅读设置 → 发送确认阈值（Token）」默认为 0，关闭提醒。设置正整数后，通过发送按钮或 Enter 提交新草稿时，用当前模型的 SillyTavern tokenizer 统计本条输入（含消息封装）。超出阈值或计数失败时先询问是否继续发送。取消会保留草稿，继续后才清空输入、显示待发送消息并开始发送延迟。

挂载待发送卡片时复用已挂载的历史消息，已显示的历史消息保持原有正则深度。等待结束后刷新助手快照，并在正式列表刷新时计算已提交的消息深度。历史正文的正则结果相同时复用已挂载的正文和 HTML 卡片。加载日志分别记录卡片挂载、挂载后至下一次浏览器绘制机会和实际配置的等待阶段。绘制机会由浏览器帧回调估计。

挂载待发送卡片时聊天列表跳到最底部。等待期间向上回读时，正式请求启动会保留当前视口。AI 回复完成后，列表把该回复卡片的开头对齐到可视区顶部。短回复下方留出对齐所需的空间，用户可以继续滚动查看历史。

角色聊天成功加载、聊天位置保存并解除 loading 后，以及回复保存、自动填表完成后，延迟 150ms 在后台读取关联世界书，并分批准备完整历史（下次发送）和去除末条回复的历史（重新生成）所需的数据库文本与表格宏，同时分片预热纯历史正则。刷新后直接进入角色聊天也会触发，无需先聚焦或输入文字。切换聊天取消旧任务，读取失败不调度；立即发送时正常取消预热并补齐所需计算。世界书沿用 API 的 60 秒读取缓存，缓存失效后正常重新读取；同一路径的进行中读取可复用。资料预加载不会调用模型生成接口，也不会提前抽取世界书概率、展开动态宏或进行最终上下文裁剪与计数。

数据库缓存仅保留两份内存结果；保存聊天时清空，聊天、消息正文、快照、数据库配置或种子改变后重新准备。用户新输入仍完整参与正式请求。加载日志增加“预加载下次生成资料”；预加载失败不会阻止下次发送，下次会正常重试准备。

后台预加载还会分片准备历史消息中不依赖宏变量的提示词正则结果，并在输入框获得焦点或输入时补充预热。缓存按正则配置、适用深度、消息正文匹配，仅在内存保留按历史增长的最多 4096 项、800 万字符；含宏的正则、宏展开、世界书激活与精确计数仍实时执行。使用现有 300 楼测试副本做本地对照，构建提示词的冷耗时约 764ms，缓存命中后约 10ms，消息内容逐项一致。这只是构建阶段的对照，不代表模型返回速度。日志新增“构建提示词与展开宏”，便于区分本地构建、资料读取和模型接口耗时。

## 新消息

1. 检查是否正在切换、生成，若有未保存聊天先等待保存。
2. 校验连接和预设，对输入运行输入正则。
3. 组装请求历史并设置 busy，展示“准备上下文”。
4. 启用了指定远程原模块时，确保环境就绪并发送 `generation_started`，随后准备角色变量。助手就绪的新消息路径先添加并保存用户楼层，再等待 `message_sent`。前置保存和此事件内的助手聊天写入优先走 [增量接口](sillytavern-integration.md)，等待后端确认落盘。事件写入后的列表刷新合并到请求启动时的刷新，发送失败时由收尾刷新。重试不新增用户楼层。
5. preparePrompt：读取关联世界书列表和内容，读取当前数据库，展开数据库宏，进入 fitPrompt。
6. fitPrompt：激活世界书、处理提示词正则与宏、组装完整历史；按世界书预算和上下文上限调用后端 tokenizer。需要裁剪时二分搜索历史起点，每个候选都可能重新构建并计数，已激活结果保持稳定。
7. generationBody 复制最终请求消息。非助手前置保存路径此时添加用户楼层、清空输入框并尝试增量保存，兼容回退保存整段聊天。
8. 添加空 AI 楼层，启动模型请求链路后刷新可见消息窗口。响应头日志记录实际发出的请求是否启用流式，以及收到的响应是否为 SSE。
9. 流式回复每 90ms 最多刷新一次当前消息，更新 Markdown/HTML 显示；普通 JSON 响应使用同一后处理。
10. 完整回复且助手就绪时，优先使用增量接口保存模型原文。页面隐藏时等恢复可见，再派发 `message_received` 并开始事件超时计时；等待页面恢复的时间单独记入加载日志。该事件内的助手聊天写入也优先使用增量接口。脚本处理失败时保留已保存的回复并提示；写入结果无法确认时阻止后续保存，重开聊天以读取落盘状态。之后应用输出正则，必要时执行本地角色变量适配，维护分支及变量。
11. 优先使用增量接口保存最终回复，记住聊天入口。完整回复且助手就绪时，在页面可见后解除 busy 并发送 `generation_ended`。保存成功后才继续自动填表和下次资料预加载。角色脚本也可能自行产生保存，请求次数取决于实际写入。

生成停止或断流会保留已收到内容；无有效重生成结果时恢复旧回复。事件完整细节见 [远程助手](remote-script-runtime.md)，消息/分支/变量改动需一起检查，不能把生成成功等同于所有后处理和落盘成功。

APK 中的普通对话请求通过更新插件的本机后台生成接口启动。SillyTavern 继续处理原有模型接口和认证，插件在 Termux 进程内临时保留响应。WebView 按位置读取回复，切回页面时继续读取；同一个读取请求的重试不会重新调用模型。普通聊天和资料库总结没有生成总时限。点击停止会同时请求取消后端任务。后台收到的失败提示在恢复可见后显示。

支持原生倒计时的 APK 在等待发送时启动 Android 前台服务。切到后台后，原生计时到期会通知 WebView 继续准备请求，Termux 确认接手后结束服务。取消发送、离开聊天页面或关闭 APK 任务也会结束服务。手机从最近任务中移除 APK 或系统结束其进程时，仍在页面中等待或准备的消息会停止发送。网页和旧 APK 使用原有页面计时器。

APK 在启动任务前记录任务 ID、聊天身份和已保存的聊天版本。后台任务也保留这些信息，以便 APK 来不及写入本地存储时重新找到任务。若 APK 页面被销毁，重新打开时会加载对应聊天、校验版本，并从头读取同一个任务。回复原文先落盘，再运行角色脚本和其他后处理。聊天保存成功后才释放后台结果。短暂断开后可以点发送继续恢复；聊天版本已变动时会停止恢复，以免覆盖现有记录。

结果保留在 Termux 内存中，APK 确认保存后释放，没有按时间清理的期限。达到 64 个后台任务上限时，新任务优先回收已结束且没有聊天恢复信息的任务，其次回收最早启动的已结束任务。进行中的任务保留。Termux 中的酒馆进程退出或结果被回收后，尚未保存的回复无法恢复。此保留策略由更新插件提供，更新后需重启 Termux 中的 SillyTavern。缺少后台生成接口的旧插件仍走直连请求。

## 最近请求记录

“对话工具 → 最近请求记录”覆盖对话发送、重试、重新生成、助手脚本生成及资料库填表与总结。日志从最终请求采集消息，包含发送用正则和生成处理器的结果。启用了提示词后处理时，日志异步调用 SillyTavern 的 `/api/backends/chat-completions/process`，用与生成端点相同的规则取得后处理后的消息。此查询不调用模型，也不改变生成请求；查询失败时面板标明展示的是提交给后端的原始消息。记录包含模型、来源、请求状态和收到的回复，可按来源筛选、搜索与复制。每个标签页最多保留 10 条，刷新后清空。自动记录的开关保存在浏览器本地。

## 重新生成

共同经过校验、世界书、正则宏、精确计数、上下文裁剪。

区别是去掉末条 AI 回复构建请求；前置复制末条回复用于失败恢复；计数完成后复制末条回复为新候选、保留 swipes/swipe_info，启动请求链路后刷新列表。没有新增用户楼层的前置 saveChat，但已有未保存数据时仍会等待保存。完成后同样整段保存并解除 busy。

## 需要测量的潜在开销

| 阶段 | 开销 | 后续应测量 |
|---|---|---|
| 世界书读取 | 列表与正文请求，缓存可能被其他操作清除 | 请求次数、等待时间、缓存命中 |
| 上下文准备 | 对历史运行正则/宏并建立新消息数组 | 构建耗时、历史长度、正文大小 |
| 精确计数 | 多个串行 HTTP tokenizer 请求；不同消息通常不能命中精确缓存 | 调用次数、每次耗时、裁剪迭代数 |
| 新消息前置保存 | 整段结构复制、JSON 序列化、传输和后端落盘 | 保存 payload 大小、前端复制时间、后端响应时间 |
| 重新生成复制 | 末条回复可能附带大量候选与数据库快照 | 复制大小和耗时 |
| 可见区刷新 | 新增楼层改变消息深度，可能使保留窗口内消息重新渲染 | 重绘次数、HTML iframe 重建次数 |
| 流式刷新 | Markdown 转换、清理及 iframe 创建在主线程执行 | 每次刷新耗时、脚本是否重复启动 |
| 结束保存 | 保存完成前 busy 不解除，看起来仍不能继续操作 | 流结束至解除 busy 的时间 |

## 下一步建议

先采集上述各阶段耗时，把“点击至模型请求发出”和“模型请求至首字”分开统计。优先处理确定重复的构建、计数和重绘，再评估保存策略。未经恢复测试，不将必要的保存直接移至后台，也不使用粗略 Token 估算替代精确预算。
